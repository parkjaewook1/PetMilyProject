# 트러블슈팅 및 리팩토링

2024년 팀 프로젝트에서는 다이어리, 방명록과 Spring Boot API·React 화면 연동을 담당했습니다. 로그인과 JWT 발급, 초기 Refresh Token Rotation은 팀에서 구현했습니다. 프로젝트를 마친 뒤 기존 인증 흐름과 회원·관리자 API를 개선하면서 아래 문제를 해결했습니다.

## 프로필에 필요한 정보만 조회하기

**문제 및 원인**

일반 회원으로 다른 회원의 프로필을 조회하자 HTTP 200 응답에 비밀번호 해시와 주소까지 포함되어 있었습니다. 원인은 Member 전체를 조회한 뒤 그대로 JSON으로 직렬화하는 방식이었습니다. 프론트엔드에서 해당 정보를 표시하지 않더라도 API 응답에는 남아 있었습니다.

**해결**

친구 목록과 미니홈피에 필요한 공개 정보와 본인 또는 관리자가 사용하는 상세 정보를 DTO로 분리했습니다. MyBatis에서도 필요한 컬럼만 조회하도록 쿼리를 수정했습니다. 공개 조회에서는 ID와 닉네임을 조회한 뒤 프로필 이미지 URL을 추가합니다. Member의 비밀번호는 Jackson WRITE_ONLY로 설정해 JSON 응답에 포함되지 않도록 했습니다.

| 조회 | 응답 범위 |
| --- | --- |
| 타인 프로필 | `id`, `nickname`, `imageUrl` |
| 본인 또는 JWT와 DB의 관리자 권한이 모두 확인된 사용자 | 편집에 필요한 이메일·이름·주소·전화 등. 비밀번호 및 인증·복구 비밀값 제외 |
| 관리자 목록 | `id`, `username`, `nickname`, `gender`, `birthDate`, `inserted`, `role` |

타인 프로필의 응답 정보만 제한하고 기존 인증 조건은 유지했습니다.

**검증 결과**

실제 MariaDB를 연결한 HTTP 테스트에서 타인 프로필은 공개 필드 3개만 반환하고, 본인과 관리자의 상세 응답에도 비밀번호가 포함되지 않는 것을 확인했습니다. 친구 목록, 프로필 이미지와 회원 수정 화면에 필요한 정보도 유지했습니다.

## 권한이 바뀐 계정의 기존 JWT

**문제 및 원인**

DB에서 관리자 권한을 일반 회원으로 변경했는데도 기존 JWT로 회원 목록을 조회할 수 있었습니다(HTTP 200). JWT의 서명과 만료 시간을 검증하더라도 role claim에는 발급 당시의 권한이 남아 있었기 때문입니다.

**해결**

관리자 API에서는 필터 체인의 JWT 권한 검사에 더해 Service에서 현재 DB 권한을 확인하도록 수정했습니다. 관리자 권한이 새로 부여되더라도 기존 일반 회원 토큰으로는 관리자 API에 접근할 수 없습니다. 토큰을 재발급할 때도 기존 claim이 아닌 현재 DB 권한을 사용하도록 변경했습니다. [토큰 교체 흐름](AUTHENTICATION.md#refresh-token-재발급과-로그아웃)

**검증 결과**

권한 변경이 DB에 반영된 후 다음과 같이 확인했습니다.

- 기존 관리자 JWT로 회원 목록 조회 및 삭제 요청: 403
- 새 로그인 또는 Refresh로 재발급된 ROLE_USER 토큰으로 관리자 API 요청: 403
- 삭제된 계정의 기존 관리자 Access Token 및 Refresh 요청: 401

모든 API의 Access Token을 즉시 폐기하는 전역 denylist를 구현한 것은 아닙니다.

## 비밀번호를 그대로 두고 프로필 저장하기

**문제 및 원인**

비밀번호를 변경하지 않고 프로필을 저장할 때, 비밀번호 필드를 생략하면 테스트 DB의 NOT NULL 제약으로 HTTP 500이 발생했습니다. 빈 문자열을 보내면 저장은 성공했지만(200), 기존 비밀번호로 로그인할 수 없었습니다(401). Service에서는 새 비밀번호가 있는 경우에만 해시를 생성했지만, MyBatis의 UPDATE 쿼리는 항상 password 컬럼을 수정하고 있었습니다.

**해결**

비밀번호 필드를 생략하거나 null 또는 빈 문자열을 전달하면 동적 UPDATE에서 password 컬럼을 제외하도록 수정했습니다. 새 비밀번호를 입력한 경우에만 형식을 검증하고 BCrypt를 한 번 적용합니다. 공백만 입력한 경우는 비밀번호 변경 요청으로 판단해 유효성 검사에서 거부합니다.

**검증 결과**

비밀번호를 생략하거나 null·빈 문자열로 수정했을 때 저장이 성공하고(200), 기존 해시와 비밀번호 로그인이 유지되는 것을 확인했습니다. 정상적으로 비밀번호를 변경했을 때는 기존 비밀번호로 로그인하면 401, 새 비밀번호로 로그인하면 200이 반환되었습니다.

## 회원 삭제 중 하나의 작업이 실패하면

**문제 및 원인**

회원 삭제 기능에서는 연관 기록을 보존하면서 삭제 가능한 계정만 정리해야 했습니다. 회원 삭제가 FK 제약으로 실패할 경우, 앞서 삭제한 인증 데이터만 사라지는 문제도 방지할 필요가 있었습니다.

**해결**

현재 관리자만 회원 삭제를 요청할 수 있도록 했습니다. 삭제 트랜잭션에서 대상 회원 행을 `FOR UPDATE`로 잠그고 관리자 계정인지, 연관 데이터가 있는지 확인합니다. 자동으로 생성된 다이어리도 연관 데이터에 해당하므로 삭제가 제한될 수 있습니다. 삭제 가능한 일반 회원은 Refresh Token과 로그인 상태를 정리한 뒤 회원 행을 삭제합니다. 세 작업을 하나의 DB 트랜잭션으로 묶어 실패하면 모두 롤백되도록 구현했습니다. 파일 삭제는 이 과정에 포함하지 않았습니다. DB 트랜잭션으로 디스크 파일까지 복구할 수 없기 때문입니다.

**검증 결과**

| 실제 HTTP 검사 | 결과 |
| --- | --- |
| 비로그인 요청 / 일반 회원 | 401 / 403 |
| 대상 회원 없음 | 404 |
| 관리자 계정 또는 연관 데이터가 있는 회원 | 409, 대상과 연관 데이터 보존 |
| 연관 데이터가 없는 일반 회원 | 204, 회원·Refresh·로그인 상태 정리 |
| 추가 FK 제약으로 마지막 삭제 실패 | 409, 회원과 앞서 삭제한 인증 데이터 모두 보존 |

실제 MariaDB를 연결한 HTTP 테스트에서 회원 삭제가 FK 제약에 걸리면 앞서 삭제한 인증 데이터까지 롤백되는 것을 확인했습니다.

## UI 및 반응형 개선

메인 화면뿐 아니라 회원, 게시판, 미니홈피에도 종이색 배경과 자주색 포인트, 얇은 구분선을 적용했습니다. 색상과 폰트, 입력창, 버튼의 기본 스타일을 디자인 토큰으로 정리해 화면마다 일관되게 사용했습니다.

모바일 관리자 목록은 각 항목에 라벨을 붙인 세로 목록으로 변경했습니다. 친구 패널과 채팅창의 화면 넘침 및 스크롤 문제도 수정했습니다. 입력 필드에 레이블을 연결하고 메인 사진을 키보드로 선택할 수 있도록 개선했습니다. [브라우저 테스트](TESTING.md)
