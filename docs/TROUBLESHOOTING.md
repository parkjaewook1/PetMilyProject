# 트러블슈팅 및 리팩토링

2024년 팀 프로젝트에서는 다이어리·방명록과 Spring Boot API–React 연동을 맡았다. 로그인과 JWT 발급, 초기 Refresh Token Rotation은 팀에서 구현했다. 프로젝트 종료 후 Role 표현과 Axios 재요청을 개선하고, 회원·관리자 API에서 다음 문제를 재현해 수정했다.

## 프로필에 필요한 정보만 조회하기

**문제 및 원인**

일반 회원으로 다른 회원의 프로필을 조회했을 때 HTTP 200 응답에 비밀번호 해시와 주소가 포함됐다. 전체 Member를 SELECT한 뒤 그대로 JSON으로 직렬화했기 때문이다. 프론트에서 해당 필드를 표시하지 않아도 네트워크 응답에는 그대로 남았다.

**해결**

친구 목록과 미니홈피에서 필요한 공개 필드와 본인 또는 관리자가 사용하는 편집용 상세 필드를 DTO로 분리했다. MyBatis에서도 각각의 조회에 필요한 컬럼만 SELECT하도록 변경했다. 공개 조회에서는 ID와 닉네임을 조회하고 이미지 URL은 프로필 조회에서 보완한다. Member의 비밀번호는 Jackson WRITE_ONLY로 설정해 응답 직렬화에서도 제외했다.

| 조회 | 응답 범위 |
| --- | --- |
| 타인 프로필 | `id`, `nickname`, `imageUrl` |
| 본인 또는 JWT와 DB 모두 관리자인 호출자 | 편집에 필요한 이메일·이름·주소·전화 등. 비밀번호 및 인증·복구 비밀값 제외 |
| 관리자 목록 | `id`, `username`, `nickname`, `gender`, `birthDate`, `inserted`, `role` |

타인 프로필의 응답 필드만 제한했으며 기존 인증 조건은 유지했다.

**검증 결과**

실제 MariaDB와 HTTP 환경에서 타인 프로필 응답이 공개 3개 필드만 반환하고, 본인 및 현재 관리자의 상세 응답에도 비밀번호가 포함되지 않는 것을 확인했다. 친구 목록·프로필 이미지·회원 수정 폼에 필요한 정보는 유지했다.

## 권한이 바뀐 계정의 기존 JWT

**문제 및 원인**

DB에서 관리자 권한을 일반 회원으로 변경한 뒤에도 기존 관리자 JWT를 사용하면 회원 목록 API가 HTTP 200으로 응답했다. 서명과 만료 시간을 검증하더라도 JWT의 role claim에는 발급 당시 권한이 남기 때문이다.

**해결**

관리자 API는 필터 체인에서 JWT의 관리자 권한을 검사하고, 서비스에서 호출자의 현재 DB 권한을 다시 확인하도록 수정했다. 반대로 DB에서 관리자로 승격되어도 기존 일반 회원 토큰만으로는 관리자 API에 접근할 수 없다. 토큰 재발급 시에는 이전 claim을 복사하지 않고 현재 DB 권한으로 새 토큰을 발급한다. [토큰 교체 흐름](AUTHENTICATION.md#refresh-token-재발급과-로그아웃)

**검증 결과**

권한을 회수한 변경이 커밋된 후 기존 관리자 JWT로 목록 조회·삭제를 요청하면 403, 같은 계정으로 새로 로그인하거나 Refresh로 재발급된 ROLE_USER 토큰으로 관리자 API에 요청해도 403임을 확인했다. 삭제된 계정의 기존 관리자 Access 및 Refresh 요청은 401로 차단됐다. 모든 API의 Access Token을 즉시 폐기하는 전역 denylist는 구현하지 않았다.

## 비밀번호를 그대로 두고 프로필 저장하기

**문제 및 원인**

새 비밀번호 없이 프로필을 수정할 때 비밀번호 필드를 생략한 요청은 격리 DB의 NOT NULL 제약으로 500을 반환했다. 명시적으로 빈 문자열을 보내는 경우 저장 요청은 200이었지만 기존 해시가 보존되지 않아 재로그인은 401이었다. Service에서는 새 비밀번호가 있을 때만 해시를 만들었으나 MyBatis는 password 컬럼을 항상 UPDATE하고 있었다.

**해결**

필드 생략·null·빈 문자열은 변경 없음으로 처리하고 동적 UPDATE에서 password 컬럼을 제외했다. 새 비밀번호를 입력한 경우에만 형식을 검사하고 BCrypt를 한 번 적용한다. 공백만 입력한 문자열은 변경 요청으로 판단하여 유효성 검사에서 거부한다.

**검증 결과**

생략·null·빈 문자열로 프로필을 수정하면 200으로 저장되며 기존 해시와 비밀번호 로그인이 유지됐다. 정상적으로 비밀번호를 변경한 후 기존 비밀번호 로그인은 401, 새 비밀번호 로그인은 200인 것을 확인했다.

## 회원 삭제 중 하나의 작업이 실패하면

**문제 및 원인**

회원 삭제 시 연관 기록을 지우지 않고 계정만 정리해야 하는 경우가 있다. 관련 FK에 의해 마지막 회원 삭제가 실패하면, 먼저 정리한 인증 데이터만 삭제되는 상황도 방지해야 한다.

**해결**

현재 관리자만 삭제를 요청할 수 있도록 하고, 삭제 트랜잭션에서 대상 회원 행을 `FOR UPDATE`로 잠근 뒤 관리자 여부와 연관 데이터를 검사한다. 자동 생성된 다이어리도 연관 데이터이므로 기존 회원의 삭제가 제한될 수 있다. 삭제 가능한 일반 회원은 Refresh Token과 로그인 상태를 정리한 다음 회원 행을 삭제한다. 세 작업은 하나의 DB 트랜잭션으로 처리한다. 이 경로에서 파일은 삭제하지 않는다. DB 롤백은 디스크 파일을 복구하지 않기 때문이다.

**검증 결과**

| 실제 HTTP 검사 | 결과 |
| --- | --- |
| 비로그인 요청 / 일반 회원 | 401 / 403 |
| 대상 회원 없음 | 404 |
| 관리자 계정 또는 연관 데이터가 있는 회원 | 409, 대상과 연관 데이터 보존 |
| 연관 데이터가 없는 일반 회원 | 204, 회원·Refresh·로그인 상태 정리 |
| 추가 FK 제약으로 마지막 삭제 실패 | 409, 회원과 앞서 삭제한 인증 데이터 모두 보존 |

격리 MariaDB의 실제 HTTP 검사에서 FK 실패 시 앞선 인증 데이터 정리까지 롤백되는 것을 확인했다.

## 화면을 좁게 봤을 때

메인에서 사용한 종이색 배경, 자주색 포인트와 얇은 구분선을 회원·게시판·미니홈피에도 적용했다. 화면마다 필요한 폭이 달라 색과 폰트, 입력과 버튼의 기본 규칙을 토큰으로 두고 필요한 화면에 적용했다.

좁은 화면의 관리자 목록은 표의 열을 억지로 줄이는 대신 각 항목에 라벨을 붙여 세로로 표시했다. 친구 패널과 채팅창에서는 화면 밖으로 나가는 부분과 스크롤을 손봤다. 입력에 레이블을 연결하고 메인 사진 선택을 키보드로 조작할 수 있게 했다. 대표 화면별 브라우저 확인과 실제 통신의 확인 범위는 [테스트 문서](TESTING.md)에서 확인할 수 있다.
