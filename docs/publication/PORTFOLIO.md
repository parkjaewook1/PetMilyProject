# Petmily — 이력서·포트폴리오 문안

현재 소스와 검증 문서에 근거한 후보 문안이다. 새 개선 작업은 아직 GitHub에 커밋/푸시되지 않았다. 아래 수치는 운영 트래픽·사업 성과가 아닌 격리 환경의 엔지니어링 검증 결과다.

## 이력서 프로젝트 요약

**Petmily | 반려동물 커뮤니티 | 2024.06–07, 5인 팀 / 이후 개인 개선**

- 팀 프로젝트에서 미니홈피 다이어리·방명록 중심으로 일기 CRUD, 댓글·답글·페이징, 캘린더와 Spring Boot API–React 연결에 참여.
- 팀의 기존 Spring Security·JWT 기반을 이어받아 개인적으로 회원·관리자 API의 개인정보 응답, 권한 변경, 선택적 비밀번호 수정 결함을 재현하고 보완.
- 공개/본인·관리자 프로필 DTO 및 SQL 프로젝션 분리, 현재 DB 권한 확인, 비밀번호 미변경 UPDATE 처리와 Refresh 회전 보완.
- H2·MockMvc·단위 회귀 97개, 격리 MariaDB 실제 HTTP 시나리오 8개, 실제 프론트 브라우저 검사 17개 통과 기록 확보.
- 공통 디자인 토큰을 선택 적용하고 회원·게시판·미니홈피·관리자 목록·친구 위젯의 반응형 및 포커스/스크롤 동작 개선.

**기술:** Java 21, Spring Boot 3.2.6, Spring Security, JWT, BCrypt, MyBatis, MariaDB, React 18, Vite, Axios, React Router, Chakra UI.

## 핵심 성과 5개

1. **개인정보 응답 경계 확립:** 타인 조회에서 해시·주소가 반환되는 실제 HTTP 결함을 공개 3필드/본인·현재 관리자 상세 DTO로 분리해 수정. 공개 필요 필드와 편집 필요 필드를 구분했다.
2. **관리자 권한 회수 반영:** 기존 JWT가 남아 있어도 DB 강등 후 관리자 요청을 403으로 차단. 신규 로그인 및 Refresh 재발급도 현재 DB 권한을 사용하도록 검증했다.
3. **비밀번호 선택 수정 정상화:** 생략/null/빈 입력은 해시를 보존하고, 명시적 변경만 입력 검증 후 BCrypt 처리. 기존 해시 재해싱을 방지했다.
4. **재현부터 회귀까지 검증:** H2와 실제 MariaDB·HTTP·Chrome 결과를 구분해 기록하고, FK 실패 시 인증 행 삭제까지 롤백되는 것을 격리 데이터로 확인했다.
5. **화면 일관성·모바일 사용성 개선:** 공통 저널 토큰과 반응형 폼/목록을 적용하고, 고정 너비 채팅·위젯의 화면 초과와 포커스/스크롤을 보완했다.

성능 향상률, 비용 절감률, 사용자 수 증가, 운영 보안 감사 완료 수치는 측정 근거가 없어 기재하지 않는다.

## 문제 → 원인 → 해결 → 검증

### 타인 프로필의 비밀번호·주소 노출

- 문제: 일반 회원 JWT로 다른 회원 GET을 요청했을 때 저장된 BCrypt 해시와 주소가 응답에 포함됨.
- 원인: 전체 Member SELECT 결과를 그대로 JSON 직렬화. 프론트에서 항목을 감추는 것으로는 응답 노출을 막지 못함.
- 해결: 공개 DTO와 본인/현재 관리자 상세 DTO, 각각의 허용 필드 SQL을 분리. 비밀번호는 도메인에서도 WRITE_ONLY로 방어하고 로그/오류 응답을 정리.
- 검증: 실제 MariaDB/MyBatis→HTTP JSON의 필드 집합 검사. 공개 id/nickname/imageUrl만 허용, 본인 상세에서도 비밀번호 제외. 친구/프로필 사진과 회원 수정 폼 데이터 요구도 확인.

### 관리자 강등 이후 기존 JWT 권한 유지

- 문제: DB ADMIN을 USER로 바꿔도 기존 JWT로 관리자 목록 200.
- 원인: 토큰 서명·만료·role claim만 검사하고 현재 DB 권한을 조회하지 않음.
- 해결: 관리자 서비스 진입 시 현재 계정을 조회해 JWT와 DB 권한을 함께 검사. Refresh도 과거 claim을 복사하지 않고 현재 DB 기준으로 발급.
- 검증: 실제 로그인 → fixture DB 강등 → 구 JWT 목록/삭제 403, 새 로그인 JWT 403, 구 Refresh로 발급한 JWT도 403. 삭제된 계정과 재사용 Refresh도 차단.
- 한계: 모든 일반 API에 Access Token denylist를 구현한 사례가 아니며, 모든 동시 요청 경쟁 상태를 검증한 것도 아님.

### 비밀번호를 바꾸지 않는 프로필 수정 실패

- 문제: 필드 생략은 NOT NULL 제약에서 500, 빈 문자열은 해시 손상과 기존 비밀번호 로그인 401.
- 원인: 서비스는 비어 있지 않을 때만 encode하지만 MyBatis는 password 컬럼을 항상 UPDATE.
- 해결: null/빈 입력을 변경 없음으로 통일하고 동적 UPDATE에서 제외. 명시적 비밀번호만 형식 검사·BCrypt 한 번 적용.
- 검증: 생략/null/빈 문자열의 기존 해시 일치·재로그인, 정상 변경 시 구 비밀번호 거부·신규 허용, 해시 문자열의 재입력 거부. 실제 브라우저 수정 폼의 미입력 저장도 확인.

## 면접에서 설명할 핵심 개념

| 질문 | 설명할 내용 |
| --- | --- |
| 서명이 유효한 JWT를 왜 다시 DB로 검사하나요? | 유효한 토큰은 과거 발급 권한을 증명하지만 현재 관리자 자격을 보증하지 않는다. 관리자 요청에서는 현재 DB 상태를 추가 확인했다. 조회 비용과 즉시 회수 요구의 선택이다. |
| DTO를 쓰면 무엇이 달라지나요? | UI 숨김과 달리 응답 자체에서 비밀값을 제거한다. SQL 프로젝션까지 분리해 불필요한 개인정보를 공개 조회에서 읽지 않는다. |
| 비밀번호를 왜 그대로 다시 저장하면 안 되나요? | 해시는 원문이 아니다. 기존 해시를 새 입력으로 encode하면 로그인 원문과 일치하지 않게 된다. 변경 없음은 UPDATE 제외로 표현한다. |
| 트랜잭션이면 파일도 롤백되나요? | DB 트랜잭션은 파일 삭제를 자동 복구하지 않는다. 관리자 삭제는 연관 데이터가 있으면 제한하고 파일 작업을 호출하지 않았다. |
| Refresh 회전은 무엇을 보완했나요? | 현재 DB 권한/계정, 저장된 토큰/만료를 검사하고 구 토큰 삭제·새 토큰 저장을 묶었다. jti로 동일 시점 토큰 충돌을 피하고 구 토큰 재사용을 검사했다. |
| H2 통과 후 왜 MariaDB 검사를 했나요? | 실제 드라이버, SQL 문법·타입 매핑, FK·InnoDB 트랜잭션과 네트워크/CORS를 별도로 확인하려고 했다. 재구성 테스트 스키마와 운영 스키마 동일성은 별개다. |
| 본인이 초기 인증 전체를 만들었나요? | 아니다. 초기 인증 기반은 팀의 구현이며, 이후 개인 작업은 분석·결함 재현·구체적인 보완과 검증이다. |
| 지금 배포해도 되나요? | 아니다. 비밀값 이력과 JAR 패키징 정리가 선행돼야 하며, 운영 HTTPS/OAuth/메일/DB 검증도 남아 있다. |

## 공개할 때 유지할 한계 문장

“검증은 운영 데이터를 사용하지 않은 격리 환경에서 수행했습니다. 운영 DB/HTTPS·외부 OAuth·실제 메일·모든 기능/경쟁 상태의 검증 완료를 뜻하지 않습니다.”

## 웹 포트폴리오 적용 후보

`portfolio/PetmilyModal.patch`는 접근 가능한 Web-Portfolio 저장소의 기존 Petmily 모달에 후속 개인 개선/검증 섹션을 더하는 후보이다. 기존 팀 역할과 초기 인증 기반 설명은 유지한다. 대상 원본은 수정하지 않았고 `git apply --check`만 통과했다. 해당 저장소의 기존 미추적 이미지도 보존했다. 새 문서 링크는 공개 완료 전에는 확정하지 않는다.
